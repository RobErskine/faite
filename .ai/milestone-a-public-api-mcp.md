## 5. The three traps

### 5.1 Key scopes are unenforced — and the plugin is already global

**Do not "403 any request carrying an API key" at `/api/sync/*`. That breaks the desktop shell.**

D2a already set `enableSessionForAPIKeys: true`, deliberately global. The desktop shell mints a key via `/api/desktop/handoff` (`src/server/desktop/routes.ts:57`) and presents it everywhere, so `useSession()` sees a desktop login as signed-in rather than sync authenticating while the header still offers "Sign in". That is correct.

**No live vulnerability today** — the only consumer is desktop, whose keys are *meant* to be full-session-equivalent.

But `auth-tokens.ts` says, in its own header:

> *"if this plugin ever grows a SECOND consumer — e.g. EI-50's original vision of a user-generated, intentionally scoped read-only external API token — that token would ALSO be full-session-equivalent the moment it's created… Revisit `enableSessionForAPIKeys` (narrow it to specific routes, or start actually checking `permissions`) **before shipping that second consumer, not after**."*

**A3 is that second consumer.** A2 must make scopes real first: desktop keys keep full equivalence, user keys are narrow and rejected at `/api/sync/*` + `/api/places/*` **by scope, never by "is it an API key"**.

### 5.2 A write is a push, not a database write

`docs/API.md`, verbatim: **"a REST/MCP write is not a database write. It is a push."**

Every synced write does three things together inside one `transactionSync` in `UserDurableObject.push()`: writes the row, allocates a `version` from `sync_meta`, writes a `field_clocks` row per changed field. Skip the version and no device learns the row changed. Skip the clocks and the next client push wins by default — the API's write vanishes, looking like a sync bug.

- Route writes through `stub.push()`. Do **not** refactor `push()` (`docs/SYNC.md:344-350`).
- **404 before building an entry** on an unknown id — a patch for a non-existent row INSERTs `FIELD_DEFAULTS` placeholders with no `field_clocks`, precisely the EI-68 mechanism.
- `MAX_PUSH_ENTRIES` (500) is **not enforced** on the `pushTransportFor` path; it bypasses `parsePushRequest`. Batching must cap itself.
- Upside: the P4 broadcast fires inside `push()` and a server push has no `originWs` — **an API write wakes every connected device for free**.

### 5.3 The server HLC is creates-only

`serverHlcClock()` is documented valid **for creates only** and is **per-isolate** — it resets when the Worker recycles, so two isolates can emit the same `(phys, counter, "server")` and an update silently loses. `src/server/service/hlc.test.ts:62` pins the flaw:

```ts
expect(serverHlcClock()()).toBe(serverHlcClock()());
```

Email ingest never hits it (creates only). MCP `complete_todo` and `PATCH /api/v1/todos/{id}` both would. **A4 fixes it; A5 and A6 writes are blocked on it.** Approach: persist node id + last HLC in the DO's `sync_meta` — the DO is single-threaded per user, so a DO-owned clock closes the hole and fits `serverHlcClock(nodeId)` with no call-site changes.

Hard rules: **do not invent another sentinel HLC** (`docs/SYNC.md:207-210`), and **do not change merge semantics to make a transport work** (`.ai/lessons.md` — bitten twice).

## 6. Parity gaps in the service layer (fix in A5)

`src/lib/service/todos.ts` is a **hand-maintained mirror** of `src/lib/store/repositories.ts` — it can't import it, because `tsc -p tsconfig.worker.json` type-checks whole imported files and even `import type` would drag Dexie/`localStorage` into the DOM-less program. It has drifted:

1. **`reminderTime`** — never resolves the list's `defaultReminderPresetId`; API-created todos silently get no reminder
2. **`parentId`** — omitted from the server input type; builder hard-codes `null`
3. **No `todoEvent` "created" row** — `repositories.ts` always emits one; `lib/todo-timeline.ts:56` assumes it. Email- and API-created todos have empty history today
4. **`updatedAt`** — `mutate()` stamps it on every client patch; `buildUpdateTodoEntry` does not
5. **`position`** — the pure builder's `fallbackPosition()` is the constant `"a0"`; use `UserDurableObject.nextTodoPosition()` (`docs/API.md:64-69`: don't add a second answer)

Add a parity test. Precedent: `src/server/db/schema-parity.test.ts`.

## 7. MCP design (A6)

Mirror `~/Sites/huckleberry-eco/huckleberry-dashboard` — proven in production and already consumed by Pointer.

- Remote **Streamable HTTP at `/mcp`**. No stdio (Faite has no npm library to hang it off)
- `McpAgent` (`agents` SDK) + `McpServer`, zod tool schemas, DO binding + `migrations` entry, class re-exported from `worker.ts`
- `compatibility_flags: ["nodejs_compat"]` — required by `@modelcontextprotocol/sdk`
- Auth: `Authorization: Bearer <faite_…>`, validated in the raw fetch handler **ahead of** the agent, injected via `ctx.props`, **re-resolved per tool call** so revocation bites immediately
- Tools wrap `src/server/service/*` — never DO tables directly

**Port three workarounds** (each cost Huckleberry a debugging session):

1. **SSE → JSON unwrapping** — the `agents` SDK always answers a Streamable-HTTP POST with an SSE-framed body; minimal clients only understand JSON and hang. See `withStreamAccept()` / `jsonifyMcpResponse()`
2. **`GET /mcp` → 405** — some clients open a server→client SSE stream and block on it; this server emits no server-initiated messages, so it would idle to socket timeout. The spec permits 405
3. **Register ≥1 prompt** so the SDK advertises the `prompts` capability; some clients refuse to connect without it

First consumer: **Pointer** (EI-221), whose scope note reads *"Faite (not yet an MCP server — added later as pure config per P7)"*.

## 8. Two documents, one generator

A1 emits both; **only the public one is published** (A7):

- `openapi/openapi.json` — internal, everything including `/api/sync/*`
- `openapi/v1.json` — public, `/api/v1` only → what Scalar serves

`/api/sync/*` is the CRDT replication protocol. Publishing it makes the wire format a compatibility surface that can never change (`docs/API.md`).
